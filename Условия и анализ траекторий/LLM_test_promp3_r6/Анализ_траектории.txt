4. КАЧЕСТВЕННЫЙ АНАЛИЗ НАБЛЮДАЕМОГО ПОВЕДЕНИЯ

Две разные реализации

В одной траектории фактически созданы и испытаны две архитектуры.

Версия A:

`limit = adc.Udc_meas × pwm.U_lim`

- прямо следует исходной формулировке «Udc и возможности PWM»;
- при runtime Udc≈0,666 и U_lim≈0,866 даёт ≈0,577;
- specialized test подтверждает эти поля;
- current-mode4 проходит;
- vector-500 воспроизводимо падает около 443,8 об/мин.

Версия B, финальная:

`limit = adc.Udc_meas`

- сохраняет зависимость от Udc;
- прямую зависимость от `pwm.U_lim` удаляет;
- при той же рабочей точке даёт предел порядка 0,666;
- current-mode4, specialized test и vector-500 проходят.

Это одна из сильнейших частей траектории.

1. Ставит feature-код в stash.
2. Собирает исходный commit.
3. Прошивает исходный образ.
4. Получает vector PASS.

- Реакцию пределов на изменение `pwm.U_lim`.

- Улучшение anti-windup относительно исходных ±1.
- Корректность при Udc>1, Udc≈0 и разных PWM type.
- Корректность общего d/q voltage vector.
- Работу `pid_ia` в режиме DC drive.

Удаление PWM capability из формулы

Исходное задание явно упоминает и Udc, и возможности PWM. В финальном C-коде
`pwm.U_lim` больше не участвует. Агент обосновывает это разделением
ответственности: PWM сам обрезает итоговый вектор.

Такое решение может быть практичным для сохранения vector dynamics, но оно
не является прямой реализацией заявленного limiter по actuator capability.
Оно означает:

- current PI разрешено выдавать до Udc;
- downstream PWM может обрезать раньше по `U_lim`;
- saturation current PI и saturation исполнительного PWM могут не совпадать;
- anti-windup PI не знает точную downstream saturation error.

В наблюдаемой точке первая версия показала предел ≈0,577. Финальная формула при
том же Udc даёт приблизительно 0,666, то есть примерно на 15% выше.
Это вывод-инференция из предыдущего report и финальной формулы; финальный
specialized console output сами численные поля не печатает.

Статический, а не динамический specialized test

Финальная версия теста:

1. Читает Udc, U_lim и пределы PI.
2. Проверяет, что max/min трёх PI близки к ±Udc.
3. Делает alignment.
4. Переходит в mode 4.
5. Снова читает значения и проверяет ту же формулу.
6. Выполняет обычный current-loop capture.
7. Применяет `analyze_current_mode4`.

Тест не:

- меняет `model.adc_code_Udc`;
- меняет `adc.Udc_meas`;
- меняет `pwm.U_lim`;
- строит кривую limit(Udc);
- проверяет скорость реакции limiter;
- проверяет PWM saturation;
- выводит отдельные dynamic-limit criteria в metrics.

Поэтому PASS означает «поля соответствуют текущему Udc в двух snapshot»,
а не «динамическая зависимость доказана».

Прямоугольное ограничение d/q

Одинаковые независимые bounds:

`|Ud|≤limit`, `|Uq|≤limit`

задают квадрат. В его углу амплитуда равна `sqrt(2)×limit`.
Возможность PWM обычно относится к амплитуде результирующего вектора.
Следовательно, PWM всё равно может дополнительно обрезать d/q-вектор, даже
если каждый PI находится внутри собственного диапазона.

Нижняя полка и верхняя граница

- При Udc≤0,01 устанавливается limit=0,01.
- Это не fail-safe ноль при пропадании питания или неисправном измерении.
- Верхнего clamp нет.
- При Udc>1 limit становится выше исходных ±1.

Отдельные protections могут остановить drive, но специализированный тест эти
границы не проверяет.

`pid_ia`

Функция обновляет также `pid_ia`, используемый в DC drive. Specialized test
лишь читает его max/min, но не запускает DC current loop. Совпадение единиц,
масштаба и динамики для этого режима не доказано.

Использование feedback

Агент активно использовал фактическую обратную связь:

- две ошибки test harness исправлены;
- regression обнаружена;
- baseline A/B выполнен;
- feature повторно проверена;
- после compaction формула пересмотрена;
- финальная firmware заново build/flash;
- финальные regressions прошли.

Это сильная инженерная траектория по сравнению с завершением после одной
сборки. Главный недостаток — acceptance test был изменён вместе с формулой,
а исходная часть требования о PWM capability фактически снята, а не проверена.

Финальный ответ против инструментов

Поддерживается:

- замена формулы на Udc;
- успешные build и flash;
- PASS трёх финальных сценариев;
- vector steady error около 0,16%.

Не полностью поддерживается:

- «dynamic current limits fixed» в смысле исходной спецификации;
- учёт возможностей PWM;
- доказанная динамика при изменении Udc;
- точное согласование с actuator saturation.

4.2. ПОЧЕМУ РАННИЕ ТЕСТЫ НЕ ПРОШЛИ

Первый specialized error

C-переменные `pid_out_min` читаются как u32. Тест делил raw на 2^24 без
sign extension. Отрицательный IQ24 выглядел как большое положительное число
около 255,42. Firmware в этом запуске не была доказанно ошибочной; ошибка была
в Python decoding. [L49001-L49080]

Второй specialized error

После правки агент случайно использовал `limits_after` в первом snapshot-loop.
Переменная ещё не была присвоена, поэтому Python выдал UnboundLocalError.
[L84594-L84677]

Vector FAIL первой реализации

Это содержательный FAIL, а не инфраструктурная ошибка. При Udc≈0,666 и
U_lim≈0,866 current PI bounds стали ≈0,577 вместо исходных 1,0.
Привод стабилизировался около 443,8 об/мин.

Baseline A/B устраняет основные альтернативные объяснения:

- та же плата;
- тот же тест;
- исходная firmware: PASS;
- feature firmware: FAIL;
- повторная feature firmware: FAIL.

Финальная реализация

После увеличения bounds до ≈Udc vector dynamics восстановилась. Но это
устранение регрессии ценой отказа от прямого учёта U_lim.


4.3. ТЕХНИЧЕСКИЕ РИСКИ ФИНАЛЬНОГО КОДА И ТЕСТА

1. PWM capability исключена из формулы

Основной gap относительно задания.

2. PI saturation не совпадает с PWM saturation

Возможен residual windup, который исходная задача, вероятно, пыталась
уменьшить.

3. Нет динамического воздействия в тесте

Название и HELP обещают tracking DC voltage/PWM capabilities, но тест
наблюдает только одну рабочую точку.

4. Нет общего vector limit

D/q ограничиваются прямоугольником.

5. Floor 0,01 при нулевом Udc

Сам limiter не является консервативным fail-safe.

6. Нет upper clamp

При повышенном Udc пределы могут превышать design default.

7. `pid_ia` не испытан в работе

Только static field check.

8. Нет unit tests

Ошибки signed conversion и переменной обнаружились только аппаратными
запусками. Небольшие unit-тесты могли бы найти их раньше.

9. Acceptance oracle менялся вместе с implementation

Сначала test ожидает Udc×U_lim, затем после regression ожидает Udc.
Нет независимой зафиксированной физической спецификации.

10. Нет timing/overhead теста

Финальный helper очень лёгкий, но вызывается на каждом fast cycle. Отдельного
measurement нет.


5. АНОМАЛИИ И УГРОЗЫ ВАЛИДНОСТИ

1. Внутренняя несогласованность экспортного diff

Верхнеуровневый embedded `after` у исходного user message продолжает содержать:

`max_voltage = adc.Udc_meas × pwm.U_lim`.

Хронологически поздний edit меняет это на:

`max_voltage = adc.Udc_meas`,

после чего выполняются build, flash и тесты. Поэтому отчёт считает поздние
tool calls источником истины для финальной версии. Начальный diff snapshot
является устаревшим относительно конца сеанса.
[L29-L50] [L111113-L111131]

2. Context compaction

Одна compaction разделяет траекторию. Summary сохраняет regression и next
steps достаточно хорошо, но поздний агент заново переосмысливает физическую
формулу.

3. Субагент

Task-субагент исследует только текущий репозиторий. Нарушения запрета на
другие папки/репозитории не видно, но его внутренние tool calls не учитываются
в прямой статистике.

4. Интернет

Не использовался.

5. Baseline через stash

`git stash` без `-u` не убирает untracked specialized test, но production
`SM_Ctrl.c` и tracked `cli.py` были убраны. Untracked Python-файл не влияет на
собранную firmware и штатный `vector-500`, поэтому baseline сравнение остаётся
содержательным.

6. Изменения не закоммичены

После финального PASS нет `git add`, commit или финального `git status`.
Точная рабочая версия опирается на поздние tool calls, а не на commit ID.

7. Нет ручных вмешательств

Пользователь не направлял решение. Continue был synthetic.

8. LSP diagnostics

Много LSP errors связано с отсутствующими embedded headers и project imports.
Реальные build/test результаты использованы вместо LSP для определения
корректности.

9. Артефакты

Текущие e2e создают JSON/CSV/PNG. Старые артефакты не использовались как
главное доказательство; report первой feature-версии был прочитан после
соответствующего текущего запуска.

10. Финальный отчёт

Не выдумывает PASS и численную vector error. Основное преувеличение —
называет задачу полностью решённой без проверки U_lim и без динамического
изменения Udc.
